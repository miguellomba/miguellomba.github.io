Handlebars Partials: build once, reuse everywhere

A 60-minute hands-on workshop for developers and template authors. This page is a complete teaching sample: objectives, timed agenda, facilitator notes, two labs with solutions, and a knowledge check.

Audience
Developers new to partials
Prerequisites
Basic HTML; Handlebars expressions, {{#if}} and {{#each}}
Format
Live or virtual, 60 minutes
Tools
Any Handlebars environment, such as the playground on handlebarsjs.com

This is an original sample written for my portfolio. It uses generic Handlebars and an invented example, and it is independent of any employer's course material.

Learning objectives

By the end of the session, learners can:

  1. Explain what a partial is and when to use one.
  2. Register a partial and call it with {{> name}}.
  3. Pass values into a partial with hash parameters.
  4. Wrap content with a partial block.
  5. Define an inline partial for reuse inside a single template.

Facilitator notes

Opening (0-5 min)

Show the same event card pasted into two templates. Ask: "A designer wants the booking line changed. How many places do you edit, and how likely are you to miss one?" Let learners name the pain before you introduce the solution.

Concepts (5-15 min)

Teach three ideas in order: a partial is a named, reusable fragment; it is called with {{> name}}; it renders with the data of the place that calls it. Demo each with the same card. Check understanding by asking learners to predict the output before you run it.

Common mistakes to watch for

  • Calling a partial that was never registered, which produces a "partial not found" error.
  • Mismatched closing tag on a partial block, such as opening {{#> panel}} and closing {{/card}}.
  • Leaving {{> @partial-block}} out of the partial, so the wrapped content disappears.
  • Relying on inherited data instead of passing parameters, which breaks when the partial is reused with a different data shape.

Pacing tip

Fast finishers can try the stretch task at the end of each lab. If a lab runs over, give the solution at the 10-minute mark and walk through it together instead of letting learners stay stuck.

Lab 1: extract a card into a partial

Scenario. A training centre's site shows event cards on its homepage and on its listing page. Both templates contain the same markup. Sample data:

{
  "events": [
    { "title": "Intro to HTML", "date": "12 Nov", "spots": 8 },
    { "title": "CSS Layout Lab", "date": "19 Nov", "spots": 0 }
  ]
}

Starter. This block appears in both templates:

{{#each events}}
  <article class="card">
    <h3>{{title}}</h3>
    <p>{{date}}</p>
    <p>{{#if spots}}{{spots}} places left{{else}}Fully booked{{/if}}</p>
  </article>
{{/each}}

Task.

  1. Register a partial named eventCard containing the card markup.
  2. Replace the card in both templates with a call to the partial.
  3. Add a showSpots parameter. The homepage hides the booking line; the listing page shows it.

Stretch. Add a highlight parameter that adds a CSS class to featured cards.

Show solution

Partial, registered as eventCard:

<article class="card">
  <h3>{{title}}</h3>
  <p>{{date}}</p>
  {{#if showSpots}}
    <p>{{#if spots}}{{spots}} places left{{else}}Fully booked{{/if}}</p>
  {{/if}}
</article>

Homepage template:

{{#each events}}
  {{> eventCard}}
{{/each}}

Listing template:

{{#each events}}
  {{> eventCard showSpots=true}}
{{/each}}

Debrief question: why is showSpots better as an explicit parameter than as a hidden rule inside the partial?

Lab 2: wrap content with a partial block

Scenario. The listing page needs the events inside a titled panel, and the same panel will wrap other content elsewhere on the site.

Task.

  1. Create a partial named panel that outputs a section with an optional heading.
  2. Use {{> @partial-block}} where the wrapped content should appear.
  3. Call it from the listing template, wrapping the event cards from Lab 1.

Stretch. Add a compact parameter that changes the panel's CSS class.

Show solution

Partial, registered as panel:

<section class="panel">
  {{#if heading}}<h2>{{heading}}</h2>{{/if}}
  {{> @partial-block}}
</section>

Listing template:

{{#> panel heading="Upcoming events"}}
  {{#each events}}
    {{> eventCard showSpots=true}}
  {{/each}}
{{/panel}}

Debrief question: what happens if you delete the {{> @partial-block}} line, and why?

Inline partials and best practices

When a fragment is only needed in one template, define it right there instead of registering it globally:

{{#*inline "badge"}}
  <span class="badge">{{label}}</span>
{{/inline}}

{{> badge label="New"}}
{{> badge label="Fully booked"}}
  • Give each partial one clear job.
  • Use camelCase names, such as eventCard.
  • Pass values explicitly with hash parameters rather than relying on inherited data.
  • Use an inline partial for single-template reuse. Register a partial as soon as two templates need the same fragment.

Knowledge check

Five questions, answered individually, then discussed as a group.

  1. Which syntax calls a partial named eventCard?
    Answer{{> eventCard}}
  2. A partial block's partial leaves out {{> @partial-block}}. What is rendered for the wrapped content?
    AnswerNothing. The wrapped content is discarded.
  3. When would you choose an inline partial over a registered one?
    AnswerWhen the fragment is only reused within a single template.
  4. Why pass hash parameters instead of relying on inherited data?
    AnswerThe partial stays self-contained and works with different data shapes, and the call shows what the partial needs.
  5. Find the bug: {{#> panel}} ... {{/card}}
    AnswerThe closing tag must match the partial's name: {{/panel}}.

Why I designed it this way

  • Problem first. Learners feel the duplication before they see the fix, so the concept has a reason to exist.
  • One idea per segment. Standard partials, then parameters, then blocks, then inline. Each lab builds on the last.
  • Demo, then do. Every concept is shown once before learners try it themselves.
  • Built-in recovery. Solutions, common mistakes and a pacing rule keep a mixed-ability group moving.
  • Check before you finish. The knowledge check tests understanding of the objectives, not memory of syntax.
